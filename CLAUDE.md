# CLAUDE.md

Diese Datei leitet Claude Code (claude.ai/code) bei der Arbeit am Code dieses Repositories an.

## Aktueller Stand

Ein `express-generator`-Gerüst (Express 5, Node >= 20.11) mit einer **von Vite gebauten React-19-SPA** als Frontend und **PostgreSQL** dahinter. Login, Sessions, Benutzerverwaltung (`/admin`) und das `freistellungen`-Schema stehen, dazu ein erstes Stück Fachlogik: Ein Teilnehmer kann unter `/teilnehmer` eine Freistellung beantragen und deren Status verfolgen. Über diese Anträge entscheidet noch niemand — keine Oberfläche für Berufstrainer oder Admins schreibt `status`, `decided_by` oder `assigned_berufstrainer_id`, alles bleibt also `offen`. Die Startseite ist weiterhin ein Platzhalter. Alles Folgende ist Gerüst zum Daraufbauen, keine gewachsene Konvention, die es zu bewahren gilt.

Es gibt keine README, keinen Test-Runner und keinen konfigurierten Linter.

## Befehle

```
npm install
npm run db:up      # startet das lokale Postgres aus docker-compose.yml (--wait: blockiert, bis es gesund ist)
npm run migrate up # wendet migrations/ an
npm run seed       # legt das LOGIN_USER-Konto an (Standard: admin/admin)
npm run dev        # Vite-Dev-Server auf :5173 + ein beobachtendes ./bin/www auf :3000 — :5173 benutzen

npm run build      # baut die React-App nach client/dist
npm start          # startet ./bin/www auf PORT (Standard 3000) und liefert client/dist aus
npm run db:down    # stoppt die Datenbank (mit -v wird auch das Daten-Volume verworfen)
```

In der Entwicklung **http://localhost:5173** öffnen, nicht :3000. Vite liefert die App aus und leitet `/api` als Proxy an Express weiter, wodurch das Session-Cookie same-origin bleibt. Wer :3000 direkt aufruft, bekommt das, was zuletzt nach `client/dist` gebaut wurde (und einen 404 mit Hinweis, falls noch gar nichts gebaut wurde).

Die Konfiguration kommt aus `.env` im Repo-Wurzelverzeichnis (gitignored; `.env.example` ist die eingecheckte Vorlage). `bin/www` lädt sie, bevor irgendetwas anderes required wird, und `vite.config.mjs` liest dieselbe Datei über `envDir` — nur Variablen mit `VITE_`-Präfix erreichen von dort aus den Browser-Code. Echte Umgebungsvariablen haben immer Vorrang vor der Datei.

Es gibt kein `npm test`-Skript und keine Testdateien. Werden Tests gebraucht, zuerst den Runner und ein `test`-Skript in `package.json` ergänzen.

## Architektur

Der Server ist ausschließlich eine JSON-API; jede HTML-Route ist eine clientseitige Route.

- `bin/www` — ausführbarer Einstiegspunkt. Lädt `.env` und verantwortet danach den HTTP-Server, die Port-Normalisierung und die Behandlung von `EADDRINUSE`/`EACCES`. Es required `app.js`; `app.js` selbst ruft niemals `listen` auf.
- `app.js` — baut die Express-App und exportiert sie: Middleware-Kette (morgan → json → urlencoded → cookie-parser → static → session), API-Router, danach der `/api`-404, der SPA-Fallback und der Fehler-Handler.
- `routes/api/*.js` — jede Datei exportiert einen `express.Router()`; `app.js` hängt ihn unter `/api` ein.
- `lib/db.js` — der eine `pg.Pool` des Prozesses, aufgebaut aus `DATABASE_URL`. Alles, was die Datenbank berührt, läuft darüber, auch der Session-Store.
- `lib/freistellungen.js` — alles, was die Tabelle `freistellungen` liest oder schreibt, im Zuschnitt von `lib/auth.js`: Die Routen bleiben dünn, und die hier geworfenen Fehler tragen einen `status`.
- `migrations/` — `node-pg-migrate`, reines SQL innerhalb von `pgm.sql()`. Neue mit `npm run migrate create <name>` anlegen; die Dateinamen tragen einen Präfix in Millisekunden seit Epoch, weil der Generator das so ausgibt und Migrationen in Dateinamen-Reihenfolge laufen — keine datumsartigen Präfixe von Hand schreiben, die sortieren *vor* den bestehenden.
- `scripts/` — `migrate.js` umhüllt die node-pg-migrate-CLI, damit sie `.env` sieht; `seed-user.js` ist `npm run seed`.

`npm run dev` begrenzt den Datei-Watcher des Servers auf `bin/`, `lib/`, `routes/` und `app.js` (`--watch-path`), statt ein bloßes `node --watch` zu verwenden. Ein bloßer Watch erfasst auch `node_modules`, sodass Vites Schreiben seines Dependency-Caches den API-Server unter dem Proxy weg neu startet. Bei einem neuen serverseitigen Quellverzeichnis ist ein weiteres `--watch-path` zu ergänzen.
- `client/` — die React-App. `vite.config.mjs` im Repo-Wurzelverzeichnis richtet Vite darauf aus (`root: 'client'`) und baut nach `client/dist`.

### Routen hinzufügen

**Neue API-Router müssen in `app.js` oberhalb des `/api`-404-Auffangs eingehängt werden**, sonst werden sie nie erreicht. Alles darunter ist der SPA-Fallback (`app.get('/*splat')`), der für jeden Nicht-API-Pfad `client/dist/index.html` ausliefert — eine neue *Seite* braucht also eine `<Route>` in `client/src/App.jsx`, keine Express-Route. Bestehende Client-Routen: `/` (Home), `/login`, `/admin`, `/teilnehmer`.

Der Fehler-Handler antwortet auf jeden Fehler mit JSON und nimmt `error.stack` nur dann auf, wenn `req.app.get('env') === 'development'` ist (Express liest `NODE_ENV` und fällt auf `development` zurück).

### Datenbank

- **Sessions** liegen über `connect-pg-simple` in der Tabelle `session` und teilen sich den Pool der App. Die Tabelle wird von einer Migration angelegt, deshalb läuft der Store mit `createTableIfMissing: false`.
- **`users`** — scrypt-Hashes, gespeichert als `salt:hash`. Logins sind case-insensitiv: Der Unique-Index liegt auf `lower(username)`, und `lib/auth.js` sucht genauso, während die ursprüngliche Schreibweise erhalten bleibt. `email` funktioniert identisch (`users_email_lower_key`), ist aber **nullable** — die Konten, die älter sind als die Spalte, haben keine, und ein Unique-Index duldet beliebig viele NULLs, was die Spalte im Admin-Formular optional hält. Anmelden kann man sich **wahlweise** mit Benutzernamen oder Adresse: `findByLogin` verodert die beiden Spalten, und das ist nur deshalb eindeutig, weil `users_username_not_email` ein `@` im Benutzernamen verbietet und die beiden Namensräume damit konstruktionsbedingt disjunkt sind. Diesen Constraint beibehalten, wenn eine der beiden Spalten angefasst wird. `users_email_shape` ist nur ein grobes Auffangnetz; die deutsche Meldung stammt aus `normalizeEmail` in `lib/auth.js`. `role` ist das **Enum** `user_role` (`admin`, `berufstrainer`, `teilnehmer`; Standard ist `teilnehmer`) — die Rollen liegen in der Datenbank, damit `auth.listRoles()` sie mit `enum_range()` für das Dropdown im Admin-Dashboard zurücklesen kann; eine neue Rolle kommt in die users-Migration (oder per `ALTER TYPE user_role ADD VALUE`), Änderungen am JS sind nicht nötig. Eine Rolle steht **mit dem Anlegen fest**: Der Trigger `users_role_immutable` weist jedes `UPDATE` zurück, das sie ändert, es gibt also weder Beförderung noch Herabstufung — stattdessen ein neues Konto anlegen. Genau deshalb setzt `upsertUser` die Rolle nur beim Insert und lässt die eines bestehenden Benutzers unangetastet. Der überflüssig wirkende Unique-Constraint `users_id_role_key` auf `(id, role)` existiert allein als Ziel des Fremdschlüssels von `freistellungen.assigned_berufstrainer_id`.
- **`freistellungen`** — `start_date`/`end_date` sind `timestamptz`: Eine Freistellung trägt eine Uhrzeit, nicht bloß ein Datum. `start_date` ist auf Anwendungsebene **inklusiv**, `end_date` **exklusiv**, ein ganzer freier Tag geht also von `00:00` bis `00:00` des Folgetages. Die Spalte `period` ist `GENERATED ALWAYS AS tstzrange(start_date, end_date, '[)')` und existiert, um den Exclusion-Constraint `freistellungen_no_overlap` zu tragen, der verhindert, dass eine Person zwei gültige Freistellungen über denselben Zeitraum hält (abgelehnte Anträge sind ausgenommen); das halboffene Intervall ist es, was eine Freistellung genau dann enden lässt, wenn die nächste beginnt. Diese Regel steckt bewusst in der Datenbank, damit zwei gleichzeitige Einreichungen nicht an einer Prüfung auf Anwendungsebene vorbeilaufen können — sie dort belassen und nicht in JS nachbauen.
  - `assigned_berufstrainer_id` ist der Berufstrainer, der die Freistellung betreut, `NULL`, bis jemand zugewiesen ist. Die Datenbank erzwingt, dass diese Person tatsächlich die Rolle `berufstrainer` hat: Die konstant gefüllte Begleitspalte `assigned_berufstrainer_role` existiert einzig, damit der zusammengesetzte Fremdschlüssel `(assigned_berufstrainer_id, assigned_berufstrainer_role) → users (id, role)` das verlangen kann. Nur `assigned_berufstrainer_id` einfügen und aktualisieren; die Rollenspalte nie selbst schreiben. `status` ist eines von `offen`, `genehmigt`, `abgelehnt`, `geschlossen`.
  - `kind` ist `NOT NULL` ohne Default, und es gibt noch nichts zu wählen, deshalb trägt `lib/freistellungen.js` die Konstante `'freistellung'` ein. Kommt eine zweite Art dazu, ist diese Konstante die Stelle dafür.
  - `freistellungen_dates_ordered` lautet `end_date > start_date`, nicht `>=`: Ein gleiches Paar ergibt ein leeres Intervall, und leere Intervalle überlappen nie — es käme also am Exclusion-Constraint vorbei.
  - Fallstrick: Weil eine generierte Spalte vor den `CHECK`-Constraints berechnet wird, scheitert ein `end_date` vor `start_date` an Postgres' Fehler aus dem Range-Konstruktor statt am benannten Check `freistellungen_dates_ordered`. Wer eine brauchbare deutsche Fehlermeldung will, prüft die Reihenfolge in der Route vor dem Insert.

`SESSION_SECRET` muss in Produktion gesetzt sein — sonst wird es bei jedem Start neu erzeugt und entwertet bei jedem Neustart sämtliche Sessions. Die Zugangsdaten in `docker-compose.yml` sind lokale Wegwerfdaten und für kein echtes Deployment gedacht.

### Authentifizierung

`express-session` läuft nach der Static-Middleware, deshalb bleiben `public/` und der gebaute Client öffentlich; das Session-Cookie (`sid`) schützt die API.

- `lib/auth.js` — `authenticate` (async, geht an die Datenbank; das erste Argument ist ein Benutzername *oder* eine E-Mail-Adresse), `upsertUser`, `createUser`, `listUsers`, `listRoles`, `listBerufstrainer` sowie die Gates `requireAuth` / `requireAdmin`. `requireAuth` antwortet mit **401 JSON**; es leitet nicht um — die Navigation gehört der React-App. `requireAdmin` antwortet mit **403**, damit der Client „anmelden“ von „nicht erlaubt“ unterscheiden kann. `scryptSync` blockiert den Event-Loop pro Anmeldeversuch rund 100 ms; das ist bei diesem Aufkommen ein bewusst in Kauf genommener Handel.
  - `createUser` fasst ein bestehendes Konto nie an (anders als `upsertUser`), damit das Dashboard nicht stillschweigend ein Passwort zurücksetzt, indem es einen Namen wiederverwendet. Es macht aus einem `23505` einen 409 und aus einem `22P02` — einer Rolle, die das Enum nicht kennt — einen 400, beides als Fehler mit `status`, die die Routen unverändert weiterwerfen. Inzwischen können zwei Unique-Indizes einen `23505` auslösen, deshalb liest es `err.constraint` aus, um zu sagen, ob der Name oder die Adresse kollidiert ist. Der Cast `$3::user_role` im INSERT ist nicht kosmetisch: Innerhalb von `COALESCE` würde pg für den Parameter sonst `text` ableiten, und das Statement scheitert, bevor das Enum überhaupt befragt wird.
- `routes/api/auth.js` — `GET /api/auth/session`, `POST /api/auth/login`, `POST /api/auth/logout`, eingehängt **vor** den geschützten Routern. Das Feld `username` im Login-Body trägt, was auch immer in das eine Identifikationsfeld getippt wurde — Name oder Adresse; der Feldname blieb der alte, damit sich das Format der Anfrage nicht ändern musste.
- `routes/api/users.js` — `GET /api/users`, `GET /api/users/roles`, `POST /api/users`, `PUT /api/users/:id/password` (204), `DELETE /api/users/:id` (204). Der gesamte Router hängt hinter `auth.requireAuth, auth.requireAdmin`. `/roles` ist **vor** `/:id` deklariert, damit der literale Pfad nie als ID gelesen wird.
  - `deleteUser` verweigert das eigene Konto des Admins (409 — es würde die Session zerstören, in der er gerade arbeitet), macht aus den `ON DELETE RESTRICT`-Fremdschlüsseln von `freistellungen` einen 409 und löscht die Zeilen des Kontos in derselben Transaktion aus der Tabelle `session`. Ohne diesen letzten Teil behielte ein gelöschter Benutzer bis zu acht Stunden lang ein funktionierendes Cookie, denn `requireAuth` schaut immer nur auf die Session.
  - `setPassword` verwirft aus demselben Grund die übrigen Sessions dieses Benutzers, behält aber die eigene `req.sessionID` des Aufrufers, damit ein Admin beim Ändern des eigenen Passworts nicht mitten im Klick abgemeldet wird. Eine Abfrage des alten Passworts gibt es nicht: Das hier ist ein Admin-Reset, und das Gate ist `requireAdmin`.
- `routes/api/freistellungen.js` — `GET /api/freistellungen`, `GET /api/freistellungen/berufstrainer`, `POST /api/freistellungen` (201), eingehängt nur hinter `auth.requireAuth`. Liste und Insert arbeiten auf den **eigenen** Zeilen des Aufrufers: Die Benutzer-ID kommt aus `req.session.user.id` und wird nie aus der Anfrage gelesen — genau das macht den Router ohne Rollen-Gate sicher. `POST` legt immer einen `offen`-Antrag an — Status und Entscheidung stehen dem Aufrufer nicht zu — und prüft `end > start` selbst, damit der Fehlschlag eine deutsche Meldung ist und nicht Postgres' Fehler aus dem Range-Konstruktor (siehe den Fallstrick unter **Datenbank**). Eine Überschneidung kommt als `23P01` aus der Datenbank zurück und wird zu einem 409.
  - `assignedBerufstrainerId` kann mitgeschickt oder weggelassen werden; es ist optional, weil die Spalte NULL bleibt, bis jemand den Fall übernimmt. In JS wird nur die **Form** geprüft. Dass die ID zu einem Konto mit der Rolle `berufstrainer` gehört, bleibt dem zusammengesetzten Fremdschlüssel überlassen, der sowohl bei falscher Rolle als auch bei unbekannter ID mit `23503` auf `freistellungen_assigned_berufstrainer_fkey` antwortet — aus Sicht des Aufrufers derselbe Fehler und eine deutsche Meldung. `assigned_berufstrainer_role` niemals schreiben.
  - `/berufstrainer` existiert, weil `/api/users` nur für Admins zugänglich ist, das Antragsformular aber trotzdem Namen nennen muss. `auth.listBerufstrainer()` beschränkt sich auf `{id, name}` für diese eine Rolle und ist damit die einzige Auflistung fremder Konten, die ein Nicht-Admin erreichen kann. Es ist ein literaler Pfad und müsste oberhalb einer `/:id`-Route stehen, falls hier je eine dazukommt.
- Geschützte Router werden als `app.use('/api/path', auth.requireAuth, router)` eingehängt. Neue Router brauchen dieses Gate ausdrücklich; einen pauschalen Schutz gibt es nicht. Für einen Router nur für Admins kommt `auth.requireAdmin` dahinter.
- Konten entstehen durch `npm run seed` (aus `LOGIN_USER`/`LOGIN_PASSWORD` sowie dem optionalen `LOGIN_EMAIL`) oder über das Admin-Dashboard unter `/admin`; beides passiert nicht beim Start, und das Hochfahren des Servers überschreibt nie ein Passwort.
- `client/src/auth/AuthContext.jsx` hält die Sicht des Clients auf die Session — es fragt beim Start einmal `/api/auth/session` ab, weil das Cookie `httpOnly` und aus JS nicht lesbar ist. `client/src/auth/RequireAuth.jsx` umschließt geschützte Routen und schickt nach `/login`, wobei es den angesteuerten Ort im Router-State merkt; mit einem `role`-Prop bildet es zusätzlich `requireAdmin` ab und zeigt eine Absage an, statt umzuleiten — einen bereits angemeldeten Besucher nach `/login` zu schicken, ergäbe nur eine Schleife.
- `client/src/pages/Admin.jsx` ist das Admin-Dashboard: die Benutzerliste plus ein Anlegeformular, dessen Rollen-Dropdown aus `GET /api/users/roles` gefüllt wird, nie aus einer fest verdrahteten Liste. `Home.jsx` verlinkt es nur für Admins.
- `client/src/reasons.js` ist die Liste der Gründe, die das Antragsformular anbietet, und die **eine Stelle, an der sie gepflegt wird**. Gespeichert wird die Beschriftung selbst — `reason` ist eine schlichte `text`-Spalte, eine Änderung der Liste braucht also keine Migration, und ältere Zeilen behalten den Wortlaut, unter dem sie eingereicht wurden. Die API besteht nur darauf, dass der Grund nicht leer und höchstens 300 Zeichen lang ist; gegen diese Liste prüft sie nicht. Sollte das je erzwungen werden müssen oder sollen sich die Gründe ohne neuen Build ändern lassen, gehört die Liste hinter einen Endpunkt (so wie `GET /api/users/roles` das Rollen-Dropdown bedient).
  - `OTHER_REASON` (`Sonstiges`) wird getrennt exportiert und steht bewusst **nicht** in `REASONS`: Die Auswahl öffnet einen nativen `<dialog>`, und was dort getippt wird, ist der gespeicherte Grund — das Wort selbst erreicht die Datenbank nie, und es gibt keine Zeile, deren Grund „Sonstiges“ lautet. Das Dropdown kann immer nur diese Beschriftung zeigen, deshalb steht der bestätigte Text darunter, mit einem Link „Ändern“ — ein bereits gewählter Eintrag löst beim erneuten Auswählen kein `change`-Ereignis aus, dieser Link ist also der einzige Weg zurück in den Dialog. `REASON_MAX` in `lib/freistellungen.js` und das `maxLength` der Textarea sind dieselben 300 und sollten gemeinsam wandern.
- `client/src/pages/Teilnehmer.jsx` ist das Teilnehmer-Dashboard unter `/teilnehmer` (`RequireAuth role="teilnehmer"`): ein Antragsformular hinter einem Button — Beginn, Ende, ein Dropdown aus `reasons.js` und ein optionaler Berufstrainer aus `GET /api/freistellungen/berufstrainer` —, Filter-Chips, die zugleich die Anzahl je Status anzeigen, und die Liste der eigenen Freistellungen: vier Spalten, wobei Berufstrainer, Anmerkung und die Zeitstempel in eine Zeile eingeklappt sind, die sich per Klick öffnet. Die `datetime-local`-Felder des Formulars werden vor dem Senden in ISO-Strings umgewandelt, damit der gespeicherte Zeitpunkt die vom Benutzer gemeinte Uhrzeit ist, unabhängig von der Zeitzone des Servers. `Home.jsx` verlinkt die Seite nur für Teilnehmer.
  - Es ist die einzige Seite mit einer gestalteten Bildsprache statt des `express-generator`-Gerüsts: ein eigener `.fs-*`-Block am Ende von `styles.css`, Tokens auf `.fs`, IBM Plex aus `client/index.html`. Zwei Dinge sind dort leicht zu übersehen. `.fs` trägt `margin: -50px`, um das `body { padding: 50px }` des Gerüsts aufzuheben und randlos zu werden — ändert sich dieses Padding, muss das hier mitwandern. Und jede Hover- oder Zustandsvariante (der aktive Chip, die hervorgehobene Zeile) ist eine Regel im Stylesheet und kein Inline-Style, denn eine Inline-Deklaration gewönne dagegen und würde die Variante einfrieren.
- `client/src/api.js` ist die einzige Stelle, die `fetch` aufruft; sie stellt `/api` voran, schickt das Cookie mit und wirft bei einer Antwort außerhalb von 2xx einen `ApiError`, der die Meldung des Servers trägt.

Express-5-Eigenheiten, die vor einer Erweiterung von `app.js` gut zu kennen sind: `express.urlencoded()` verwendet inzwischen standardmäßig `extended: false` (es wird hier trotzdem ausdrücklich übergeben), Pfadmuster akzeptieren kein nacktes `*` und keine unbenannten Wildcards mehr (daher `/*splat` für den SPA-Fallback), und ein abgelehntes Promise aus einem async-Route-Handler wird automatisch an den Fehler-Handler weitergereicht — weshalb die async-Login-Route ohne try/catch auskommt.

`public/` wird neben `client/dist` statisch ab der URL-Wurzel ausgeliefert, eine Datei unter `public/images/logo.png` wird also als `/images/logo.png` angefragt. Assets, die aus React-Code importiert werden, gehören stattdessen unter `client/src` und durch den Vite-Build.
